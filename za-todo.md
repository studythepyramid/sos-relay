Key for API, 
1. The trigger pattern — DB-column-as-queue, not a message broker. For your scale, the simplest robust pattern is: add a processed_at (or status) column to sos_pins, and have a worker process poll WHERE processed_at IS NULL every few seconds, process each row (call an LLM API for translation/fact-check), write the result, mark it processed. SQLite itself is the queue — no Redis, no Celery, nothing extra to run or that can fail independently. This is also exactly consistent with the "publish first, enrich async" principle: the pin is already public and visible the instant it's inserted; the worker finding it a few seconds later and attaching a translation/fact-check doesn't block or gate anything.

2. Keeping it alive — systemd, not a screen session. A tmux/screen session survives your SSH disconnecting, but not a reboot, and nothing restarts it if it crashes. The actual right tool is a systemd unit:

# /etc/systemd/system/sos-agent.service

Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.tar
